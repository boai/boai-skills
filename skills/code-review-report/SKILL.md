# 代码评审报告生成器

## 解决什么问题

人工代码评审容易漏：看得快就漏边界条件，看得细又太慢；不同人标准不一，同一类问题这次提、下次不提。这个 skill 把评审变成一条固定流程——**先收集变更、再对照检查清单、最后按固定模板出报告**，让每次评审的标准一致、结论可追溯。

它不替代人的判断，负责三件事：

1. 不漏掉机械性检查（空值、越界、循环引用、硬编码密钥、主线程 UI……）
2. 把问题按「必须修复 / 应当修复 / 建议优化」排好优先级
3. 每条结论都落到 `文件:行号`，评审意见可以直接贴进 PR

## 何时使用

- 功能分支开发完，合并或提测前
- 一次提交堆了很多改动，想知道风险集中在哪
- 同事发来一段代码或 diff，让你帮忙看看
- 上线前的最后一道自查

**不适用**：只是想讨论某个设计思路（直接聊）；代码还没写（先设计评审）。

## 工作流

### 第 1 步：确定评审范围

先判断用户属于哪种模式：

| 模式 | 用户给了什么 | 做法 |
|------|--------------|------|
| A 分支范围 | 仓库路径、分支名，或说「评审我当前分支」 | 用 `scripts/collect_diff.sh` 收集 |
| B 粘贴 diff | 一段 `diff --git` 内容 | 直接分析，跳过收集脚本 |
| C 文件或片段 | 文件路径，或直接贴代码 | 读文件 / 分析片段 |

模式 A 下如果用户没指定基线分支，按 `origin/HEAD` → `main` → `master` 的顺序自动探测。**探测结果要先告诉用户再继续**，例如：

> 检测到评审范围：`feature/remote-control` 对比 `main`，共 12 个文件、3 次提交。开始评审。

如果仓库不在当前目录，让用户给出绝对路径；不要猜。

### 第 2 步：收集材料

```bash
# <skill目录> 换成实际路径；安装后通常是 ~/.claude/skills/code-review-report
bash <skill目录>/scripts/collect_diff.sh \
  --repo /path/to/repo --base main --target HEAD --max-chars 60000
```

脚本会输出：仓库路径、变更统计、提交列表、变更文件清单、过滤后的 diff。过滤掉锁文件、`Pods/`、`node_modules/`、构建产物、图片、二进制等噪音（完整排除列表见脚本）。

- `--repo` 指定仓库路径，脚本可从任意目录运行
- 只想要某个目录：追加 `-- <path>`（脚本会把参数透传给 git）
- 保存到文件：`--out /tmp/review-diff.txt`；文件已存在时需加 `--force` 才会覆盖
- diff 超过 `--max-chars` 会被安全截断（不会截断半个汉字），并在报告头部标注

**空 diff**：直接告诉用户「这个范围没有可评审的改动」，不要硬编报告。

### 第 3 步：识别语言，加载对应检查清单

按变更文件的主要后缀，只读相关的 1~2 份清单，不要全部读完：

| 后缀 | 读取 |
|------|------|
| `.swift` `.m` `.mm` `.h` | `references/checklists/swift-ios.md` + `general.md` |
| `.java` `.kt` `.kts` | `references/checklists/jvm.md` + `general.md` |
| `.ts` `.tsx` `.js` `.jsx` `.vue` | `references/checklists/web.md` + `general.md` |
| `.py` `.go` `.rs` | `references/checklists/python-go.md` + `general.md` |
| 涉及登录、支付、密钥、上传、权限 | 追加 `references/checklists/security.md` |

多语言混合改动时，按文件分组审查，每组各用各的清单。

### 第 4 步：审查

**按文件审，不要按行审。** 先读完整 diff，再读必要的上下文（用 `git show <commit>:<file>` 或直接读文件），理解这段代码想做什么，然后找它哪里会出错。

对每个可疑点，问自己一句：**「什么输入、什么时序、什么状态下，这里会出错？」** 答不上来的，通常不是真问题，删掉。

审查维度：

| 维度 | 关注点 |
|------|--------|
| 正确性 | 逻辑分支、条件取反、状态机迁移、返回值、单位换算 |
| 边界与空值 | 空数组、空字符串、nil/null、0、负数、超大值、首尾元素 |
| 错误处理 | 网络/解析/文件失败是否有兜底；`try?` 是否吞掉了必须处理的错误 |
| 并发与生命周期 | 线程安全、主线程 UI、闭包捕获、Timer/通知是否注销 |
| 安全 | 密钥硬编码、日志打印敏感信息、越权、注入 |
| 性能 | 主线程耗时、循环内重复计算、列表未复用、内存增长 |
| 可维护性 | 命名、重复代码、魔法数字、超长函数、隐式耦合 |
| 兼容性 | 新旧系统版本、空数据、接口字段缺失、多语言与 RTL |

**只报告本次 diff 引入或直接放大的问题。** 老代码里的历史问题不在本次评审范围内，除非用户明确要求全量体检。

**分级标准：**

| 级别 | 判定 | 例子 |
|------|------|------|
| 🔴 阻断 | 主流程或常见操作可复现的崩溃、丢数据、资损、安全漏洞，必须改完才能合并 | 空列表取下标、明文密钥、无锁并发写、失败永不回调导致主流程卡死 |
| 🟠 严重 | 低频或边界条件才触发的崩溃，以及明确的功能缺陷、高风险隐患，应当本次修复 | 特殊字符导致的强解包崩溃、循环引用、UI 更新不在主线程、Timer 未销毁 |
| 🟡 建议 | 不影响正确性，但影响可读性、性能或后续维护 | 命名不清、重复代码、魔法数字、日志过多 |
| 🟢 好评 | 值得肯定的写法，帮团队沉淀正面样例 | 边界处理完整、错误分层清晰、测试补齐 |

### 第 5 步：写报告

保存到 `CodeReviews/<repo>-<YYYYMMDD-HHmm>.md`。用户指定了路径就用用户的；文件已存在时先问是否覆盖。

严格使用下面的模板，章节顺序和标题不要改。空的分级写 `_暂无_`，不要删章节。

```markdown
# <仓库名> 代码评审报告

- **评审范围**: `<base>` → `<target>`
- **评审时间**: <YYYY-MM-DD HH:mm>
- **变更规模**: <N> 个文件 | +<新增> / -<删除> 行 | <M> 次提交
- **评审模式**: 分支对比 / 粘贴 diff / 单文件
- **结论**: ✅ 可以合并 / ⚠️ 修复后合并 / ⛔ 暂不可合并

> 一句话总评：这批改动主要做了什么，风险集中在哪。

## 一、问题汇总

| 级别 | 数量 | 说明 |
|------|------|------|
| 🔴 阻断 | 0 | |
| 🟠 严重 | 2 | |
| 🟡 建议 | 5 | |
| 🟢 好评 | 1 | |

## 二、🔴 阻断问题（必须修复）

### 1. <一句话问题>

- **位置**: `path/to/File.swift:42`
- **现象**: 这里实际会发生什么
- **触发条件**: 什么输入 / 时序 / 状态下触发
- **修复建议**: 具体怎么改（给代码片段更好）

（每个问题都用这个四段式，一个问题一个小节。）

## 三、🟠 严重问题（应当修复）

（同上格式）

## 四、🟡 建议（可选优化）

| # | 位置 | 建议 |
|---|------|------|
| 1 | `path/File.swift:88` | 抽成常量，避免魔法数字 |

## 五、🟢 做得好的地方

- 具体指出哪段代码、为什么好

## 六、评审说明

- 本次评审覆盖了哪些文件、哪些被过滤
- 是否有截断、是否缺少上下文
- 未能确认、建议作者补充说明的点
```

### 第 6 步：自检

出报告后逐条核对：

1. **每条引用都真实存在**：运行 `bash <skill目录>/scripts/verify_citations.sh <报告路径> <仓库路径>`，脚本会检查 `文件:行号` 是否存在、行号是否越界。有 ❌ 就必须改掉或删除该条。
2. **每条问题都能回答「什么情况下出错」**：答不上来的删掉。
3. **没有把 diff 内容换个说法再抄一遍**：问题要解释风险，不是复述代码。
4. **没有编造**：不确定的地方写进「评审说明」，标注待确认，不要写成结论。
5. **结论和问题数量一致**：有阻断问题就不能写「可以合并」。

最后向用户汇报：报告路径、变更规模、各级问题数量、最该先看的 1~3 条。

## 无本地环境时（飞书 Aily / 纯对话）

没有 Git 仓库、不能跑脚本时，降级为纯提示词模式：

1. 请用户粘贴 diff（`git diff main...HEAD` 的输出）或代码片段
2. 按第 3~5 步同样审查，报告直接输出在对话里
3. 提醒用户：行号以粘贴内容为准，可能和源文件不一致

降级模式仍要遵守同一套分级标准和报告模板，不要降低标准。

## 验证方式

```bash
# 1. 生成一个带故意 bug 的演示仓库（本地产物，不影响任何真实仓库）
#    脚本会打印仓库路径，下文用 <演示仓库> 表示
bash <skill目录>/examples/make_demo_repo.sh

# 2. 收集 diff（--repo 指向演示仓库，可从任意目录运行）
bash <skill目录>/scripts/collect_diff.sh \
  --repo <演示仓库> --base main --target feature/remote-control \
  --out /tmp/demo-diff.txt

# 3. 用自带示例报告校验引用（也可以校验 AI 刚生成的报告）
bash <skill目录>/scripts/verify_citations.sh \
  <skill目录>/examples/sample-review-report.md <演示仓库>
```

演示仓库里埋了 7 类典型问题（强解包、循环引用、主线程 UI、硬编码密钥、Timer 泄漏、并发写、吞异常），正常情况下至少应被检出 6 类。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 每条都写「建议优化」，没有优先级 | 按阻断/严重/建议严格分级，阻断问题必须排最前 |
| 编造一个看起来合理的行号 | 只引用 diff 或文件里真实存在的行，最后跑 verify_citations.sh |
| 把整个文件的历史问题都算到这次改动头上 | 只评审本次 diff 引入或放大的问题 |
| 报告变成 diff 的中文翻译 | 每条写「现象 + 触发条件 + 修复建议」 |
| 有阻断问题却写「基本可以合并」 | 结论必须和问题级别一致 |
| 大 diff 直接截断就完事 | 截断要在报告头部标注，并说明未覆盖的部分 |
| 只读 diff 不看上下文就下结论 | 关键调用要看被调方实现，必要时读完整文件 |
