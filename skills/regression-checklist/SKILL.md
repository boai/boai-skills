# 回归测试清单生成器

## 解决什么问题

改完代码，测试最怕两件事：**该测的没测**（改动波及了别的模块但没人想到）和**全量回归**（不知道影响面，只能把所有功能过一遍，浪费一天）。

这个 skill 用「改动文件 → 模块 → 功能点」三层映射，再加上公共面扩散规则，把「这次要回归什么」变成一张有优先级、有验证步骤的清单。

## 何时使用

- 提测前，需要告诉测试回归范围
- 修复线上问题后，评估影响面
- 合并一个大 PR 前，自查波及了哪些功能
- 测试拿到版本，需要一份可执行的回归清单

**不适用**：改动只涉及文档 / 注释且无行为变化；想要完整的测试用例设计（用 `prd-to-testcases`）。

## 工作流

### 第 1 步：确认输入

支持三种输入，优先级从高到低：

| 输入 | 处理 |
|------|------|
| Git 范围（base..target） | 用脚本自动收集改动文件 |
| 文件列表 | 用 `--files` 直接传入 |
| 一段改动描述 | 先让用户给出涉及的文件或模块，再继续 |

如果项目里已有 `.regression-map.yml`，直接使用；没有就先用启发式规则生成一版，**并建议用户补一份模块地图**（模板见 `assets/regression-map.example.yml`）。

### 第 2 步：运行生成脚本

```bash
# <skill目录> 换成实际路径；安装后通常是 ~/.claude/skills/regression-checklist
python3 <skill目录>/scripts/generate_checklist.py \
  --repo /path/to/repo --base main --target feature/remote-control \
  --map .regression-map.yml \
  --format xlsx \
  --out 回归清单-$(date +%Y%m%d).xlsx
```

`--repo` 可从任意目录运行；`--map` 的相对路径会先按当前目录找，找不到再按仓库根目录找。`--out` 指向的文件已存在时需加 `--force` 才会覆盖。

常用参数：

| 参数 | 说明 |
|------|------|
| `--repo` | 仓库路径，默认当前目录 |
| `--base` / `--target` | Git 范围，不填 base 则自动探测 |
| `--files a.swift b.swift` | 直接指定文件列表，不读 Git |
| `--map` | 模块地图路径，默认 `.regression-map.yml` |
| `--format` | `xlsx`（默认）/ `md` / `csv` |
| `--out` | 输出路径；xlsx 不填则自动命名 |

脚本会输出：清单文件、回归项总数、P0 数量、涉及模块数、未映射文件列表。

**没有模块地图时**：脚本只会按全局规则（网络层、公共组件、多语言、登录态、启动流程）生成条目，粒度较粗。这时要提醒用户补地图，否则清单质量有限。

### 第 3 步：人工补全（这一步不能省）

脚本负责「不漏」，人负责「可用」。拿到生成结果后检查：

1. **未映射文件**：逐个判断属于哪个模块，补充到模块地图，或手工加进清单
2. **功能点粒度**：脚本按模块出条目，如果模块太大（比如「首页」包含 20 个功能），拆成具体功能点
3. **验证步骤可执行**：把「测试远程空调」改成「选择车辆 A，设置温度 24℃，点击启动，10 秒内状态变为运行中」
4. **补充业务场景**：脚本推不出的业务规则（如「连续点击 3 次只能下发一次指令」）要手工补
5. **优先级复核**：涉及车辆控制、支付、登录态的至少 P0；纯文案 P2

### 第 4 步：确认输出

输出表格固定列：`序号 | 模块 | 功能点 | 回归原因 | 优先级 | 验证步骤 | 结果`。

- `结果` 列留空，Excel 里带下拉选项（通过 / 失败 / 阻塞 / 未测），测试直接填
- 表头冻结、带筛选，优先级列 P0 标红、P1 标黄
- 未映射文件放在第二个 sheet，便于后续补地图

向用户汇报：文件路径、回归项数量、P0 项、涉及模块、未映射文件，并明确说明哪些条目是脚本推断、哪些需要人工确认。

## 扩散规则（脚本内置）

| 改动特征 | 追加的回归面 | 优先级 |
|----------|--------------|--------|
| `Network/`、`APIClient`、`Request` | 所有依赖接口的模块 | P1 |
| `Common/`、`Utils/`、`Extensions/` | 所有引用方 | P1 |
| `Localizable`、`Resources/`、`.strings` | 关键页面多语言、长文案 | P2 |
| `AppDelegate`、`SceneDelegate`、`Launch` | 全量冒烟 | P0 |
| `Login`、`Auth`、`Token`、`Session` | 登录 / 登出 / 切换账号 / 过期 | P0 |

这些规则可以在 `scripts/generate_checklist.py` 的 `GLOBAL_RULES` 里按项目情况增删。

## 模块地图格式

```yaml
project: DemoCarApp
modules:
  - name: 远程空调
    paths:
      - "Sources/Vehicle/RemoteClimateService.swift"
      - "Sources/Vehicle/Climate/**"
    priority: P0
    test_steps:
      - 选择一辆车，点击「远程开空调」
      - 检查温度参数、成功提示、失败提示
```

写地图的建议：

- `paths` 用目录前缀或 glob，不要逐个文件列，否则维护成本高
- `priority` 按业务重要性定，不要一律 P0
- `test_steps` 写「操作 + 预期」，一条一行
- 一个模块可以对应多个目录；一个目录也可以属于多个模块（共享组件）

## 无本地环境时（飞书 Aily / 纯对话）

1. 让用户提供改动文件列表或改动描述
2. 若有模块地图，粘贴给模型；没有就按目录名推断模块
3. 按同样的表格结构直接输出 Markdown，重点标注「推断项」和「待确认项」

## 验证方式

```bash
# 1. 生成演示仓库（含 .regression-map.yml）
bash <skill目录>/examples/make_demo_repo.sh

# 2. 生成清单（--repo 指向演示仓库，无需 cd）
python3 <skill目录>/scripts/generate_checklist.py \
  --repo <演示仓库> --base main --target feature/remote-control \
  --map .regression-map.yml --format xlsx --out /tmp/回归清单.xlsx
```

演示仓库的正常结果：13 条左右回归项、P0 至少 6 条、涉及车辆列表 / 远程空调 / 车门控制 / 网络层 / 多语言 / 全局，未映射文件 0 个。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 只列直接改动的模块 | 公共层、登录态、多语言、启动流程都要按扩散规则过一遍 |
| 所有条目都标 P0 | 按业务影响分级，P0 太多等于没有优先级 |
| 验证步骤写成「测试 XX 功能」 | 写成具体操作 + 可观察的预期结果 |
| 未映射文件直接丢掉 | 单列出来，提示补充模块地图，否则下次还会漏 |
| 模块地图一个文件一条 | 用目录 / glob 维护，降低过期成本 |
| 把清单当测试用例 | 回归清单关注「测哪些」，用例设计关注「怎么测全」，两者互补 |
