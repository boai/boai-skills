# 需求文档转测试用例

## 解决什么问题

测试写用例有三个常见问题：**漏规则**（PRD 里一句话藏着一个校验）、**写不细**（「测试登录成功」不是用例）、**需求本身有坑但没人发现**（写用例时才发现规则矛盾）。

这个 skill 把需求拆成「功能点 → 规则 → 用例」三层：每个功能点至少覆盖正常、异常、边界；每条规则都能追溯到用例；同时把需求里的模糊点和矛盾单独列出来，交回产品确认。

## 何时使用

- 需求评审后，测试需要出用例
- 开发想提前知道这个需求要自测哪些点
- 需求变更后，评估要补哪些用例
- 上线前检查用例覆盖是否完整

**不适用**：需求还只是口头想法、没有可验证的规则（先让产品写清楚）；只需要回归范围（用 `regression-checklist`）。

## 工作流

### 第 1 步：获取需求原文

| 来源 | 做法 |
|------|------|
| Markdown / txt | 直接读取 |
| Word `.docx` | `bash <skill目录>/scripts/extract_docx.sh 需求.docx > /tmp/prd.txt`（仅 macOS，依赖系统 `textutil`；其他系统用 Word 另存为 txt） |
| 飞书文档 / 在线文档 | 让用户粘贴正文，或导出为 Markdown / PDF 后提供 |
| 原型图 | 本 skill 不识别图片，请用户补充文字说明 |

拿到原文后，先确认范围：这次只测本需求，还是包含关联的旧功能回归。

### 第 2 步：解析功能点

逐段读 PRD，把「可验证的陈述」抽出来，编号成功能点。一条规则一个编号，不要把不相关的规则合并。

输出这张表，先给用户确认再往下走：

```markdown
| 编号 | 功能点 | 触发条件 | 核心规则 | 关键字段 | 状态 | 异常分支 | 原文位置 |
|------|--------|----------|----------|----------|------|----------|----------|
| F-01 | 启动远程空调 | 点击「开空调」 | 温度 16~32℃，默认 24℃ | 温度、车辆 ID | 关闭→启动中→运行中 | 车辆离线、超时 | 3.1 |
```

解析时特别注意这些容易漏的内容：

- 「仅限」「必须」「不能」开头的限制条件
- 数字范围、长度限制、时间间隔、次数上限
- 权限与前置条件（登录、绑定、实名、开关）
- 状态之间的迁移条件
- 异常提示的文案与触发条件
- 多语言、深色模式、老版本兼容要求
- 埋点与统计口径

### 第 3 步：设计用例

先读 `references/test-design-methods.md`，按里面的方法选用例。

每个功能点的最低覆盖：

| 覆盖类型 | 最少条数 | 说明 |
|----------|----------|------|
| 正常流 | 1 | 主路径走通 |
| 异常流 | 2 | 网络失败、服务端错误、非法输入等 |
| 边界值 | 1 | 有数值/长度/时间限制时必须有 |
| 权限/登录态 | 1 | 涉及用户身份或权限时必须有 |
| 兼容性 | 1 | 涉及 UI 时至少覆盖多语言或深色模式之一 |
| 状态迁移 | 全部合法迁移 | 有状态机时，每个合法迁移一条，非法迁移至少一条 |

用例类型统一用：`功能 / 异常 / 边界 / 权限 / 兼容 / 性能 / 安全`。
优先级：`P0` 主流程与资损/安全相关，`P1` 常见异常与主要分支，`P2` 边界、兼容、低频场景。

### 第 4 步：写成用例表

固定列，不要增删：

```markdown
| 编号 | 模块 | 功能点 | 用例标题 | 类型 | 优先级 | 前置条件 | 操作步骤 | 预期结果 | 需求来源 | 执行结果 |
|------|------|--------|----------|------|--------|----------|----------|----------|----------|----------|
| TC-CLIMATE-001 | 远程空调 | F-01 启动远程空调 | 默认温度启动成功 | 功能 | P0 | 已登录、已绑定车辆、车辆在线 | 1. 进入车辆列表<br>2. 点击「开空调」<br>3. 不修改温度直接确认 | 1. 提示「指令已下发」<br>2. 10 秒内状态变为「运行中」<br>3. 温度显示 24℃ | F-01 | |
```

写用例的硬要求：

1. **前置条件可准备**：写「已登录且绑定车辆 A」，不要写「环境正常」
2. **步骤可执行**：每步是一个动作，包含具体数据（温度 15、16、32、33 各一条边界）
3. **预期结果可判定**：写「提示文案为『车辆不在线』」，不要写「提示错误」
4. **一条用例只验证一个点**：不要把成功和失败写进同一条
5. **需求来源可追溯**：填 F-01 这样的编号，方便回溯
6. **不编造需求**：PRD 没写的规则不要自己加；如果认为应该有，写进「待确认问题」

### 第 5 步：导出

把用例表保存为 `测试用例-<需求名>.md`，然后导出 Excel：

```bash
# <skill目录> 换成实际路径；安装后通常是 ~/.claude/skills/prd-to-testcases
python3 <skill目录>/scripts/export_testcases.py \
  --input 测试用例-远程空调.md \
  --out 测试用例-远程空调.xlsx
```

`--out` 指向的文件已存在时需加 `--force` 才会覆盖。

脚本会生成两个 sheet：

- **测试用例**：带表头样式、冻结首行、筛选、结果列下拉（通过/失败/阻塞/未测）
- **覆盖统计**：按模块 × 用例类型统计数量，按需求来源统计覆盖

### 第 6 步：覆盖自检

1. **每个功能点都有用例**：对照第 2 步的表，逐个打勾
2. **每条规则都有对应用例**：特别是限制条件、异常提示、状态迁移
3. **正常 / 异常 / 边界 / 权限 / 兼容**五类都覆盖到了（不适用要有理由）
4. **预期结果全部可判定**：出现「正常」「正确」「符合预期」这类词就重写
5. **列出待确认问题**：需求矛盾、缺失的规则、无法验证的描述，单独成节，交产品确认
6. **用例编号唯一**：`TC-<模块缩写>-<三位序号>`

最后输出一段总结：用例总数、各类型数量、P0 数量、覆盖的功能点数、待确认问题数量。

### 第 7 步：输出待确认问题（重要）

这是本 skill 最有价值的部分之一。把读需求时发现的模糊点列出来，例如：

```markdown
## 待确认问题

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 1 | 温度步长是 0.5℃ 还是 1℃？PRD 只写了范围 | 影响边界用例数量 | 请产品确认 |
| 2 | 60 秒冷却时间按车辆还是按用户计算？ | 影响多车辆场景 | 请产品确认 |
| 3 | 车辆「离线」的判定时长是多少？ | 无法设计超时用例 | 请产品补充 |
```

不要替产品做决定，也不要因为不清楚就跳过——写出来，让问题在提测前解决。

## 无本地环境时（飞书 Aily / 纯对话）

1. 让用户粘贴 PRD 正文
2. 按第 2~4 步在对话里输出功能点表和用例表
3. 用例表用 Markdown 表格，用户可直接复制到飞书表格 / Excel
4. 说明「导出脚本需在本地运行」，不影响用例本身的质量

## 验证方式

```bash
# 用示例 PRD 跑一遍（虚构的远程空调需求）
cat examples/prd-example.md

# 生成用例表后导出
python3 <skill目录>/scripts/export_testcases.py \
  --input <你的用例表>.md \
  --out /tmp/测试用例.xlsx
```

示例 PRD 包含 7 个功能点、约 20 条可验证规则。正常产出应不少于 30 条用例，P0 不少于 8 条；自带示例用例是节选（17 条），用于演示格式和覆盖统计。示例 PRD 里故意留了 5 处模糊（温度步长、冷却范围、离线判定等），正常应至少列出 3 条待确认问题。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 一条用例覆盖多个场景 | 一条只验一个点，拆开写 |
| 预期结果写「正常显示」 | 写具体文案、状态、数值、时间 |
| 只写正常流 | 每个功能点至少 2 条异常 + 1 条边界 |
| 自己脑补 PRD 没写的规则 | 写进「待确认问题」，不要写进用例 |
| 用例没有需求来源 | 每条标注 F-xx，方便覆盖检查和变更影响分析 |
| 边界值只测中间值 | 测下界、下界-1、上界、上界+1，以及空/最大值 |
| 状态机只测正常迁移 | 非法迁移（如运行中再次启动）也要有用例 |
| 忽略多语言和 RTL | 涉及 UI 的需求至少有一条兼容用例 |
