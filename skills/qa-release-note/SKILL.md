# 提测说明生成器

## 解决什么问题

每次提测，开发都要回忆这版改了什么、影响哪里、让测试重点看什么。手写有两个后果：**漏**（自己改的记得，顺手改的忘了）和**空**（写成「修复若干问题」，测试看了等于没看）。

这个 skill 把提测说明变成一条流水线：**读 Git → 分类改动 → 翻译成人话 → 推出影响面 → 按模板成文**。产出是一份测试拿到就能开干的提测单。

核心原则：**提测单是给测试和产品看的，不是给开发看的。** 每一条改动都要回答「用户/测试能感知到什么变化」，回答不了的就标成内部改动，不要硬凑。

## 何时使用

- 功能开发完，准备交测试验证
- 版本发布前，需要一份对外说明
- 修复线上问题后，需要说明影响范围
- 测试问「这次改了哪些地方，要回归什么」

**不适用**：代码还没合并完（先合完再提测）；只是内部重构且无任何可感知变化（可以说一声，不必出单）。

## 工作流

### 第 1 步：确认必要信息

先看用户给了什么。以下信息缺了会影响成文质量，**一次性问清楚**，不要边写边问：

| 信息 | 是否必须 | 默认处理 |
|------|----------|----------|
| 提交范围（base..target） | 必须 | 自动探测 origin/HEAD → main → master |
| 版本号 | 必须 | 从最近 tag 推断，推断不出写 `[待填]` |
| 提测人 | 建议 | 取 `git config user.name` |
| 目标环境 | 建议 | 写「测试环境」，用户可改 |
| 关联需求 / 缺陷单号 | 可选 | 从 commit message 里提取，提取不到写 `[待填]` |

如果用户只说「写个提测说明」，在仓库里就直接按默认值生成，**在开头列出所用默认值让用户核对**，不要因为缺信息停下。

### 第 2 步：收集变更

```bash
# <skill目录> 换成实际路径；安装后通常是 ~/.claude/skills/qa-release-note
bash <skill目录>/scripts/collect_changes.sh \
  --repo /path/to/repo --base main --target feature/remote-control
```

输出包括：仓库、分支、提交范围、变更统计、提交列表（含 commit body）、文件变更、按目录汇总、最近 tag。`--repo` 可从任意目录运行；`--out` 写文件，已存在时需加 `--force`。

**空变更**：直接告诉用户没有可提测的改动，不要编。

### 第 3 步：分类改动

先按提交前缀分，再按实际 diff 修正：

| 类型 | 识别信号 |
|------|----------|
| 新功能 | `feat:`、新增文件、新增页面/接口/入口 |
| 缺陷修复 | `fix:`、`bugfix:`、commit body 提到问题现象 |
| 优化 | `perf:`、`refactor:`、`style:`、逻辑调整但行为不变 |
| 配置 / 构建 | `chore:`、`build:`、`ci:`、工程文件、依赖升级 |
| 资源 / 文案 | 多语言文件、图片、字体、颜色 |

**注意**：commit 前缀只是线索。要看 diff 确认，比如标了 `refactor` 却改了业务判断，那就是行为变更，必须按「优化」甚至「新功能」处理。

### 第 4 步：翻译成用户可感知的描述

这是本 skill 最关键的一步。按下面的规则改写：

| 原始 commit | 不要这样写 | 应该这样写 |
|-------------|------------|------------|
| `refactor: 统一网络层错误处理` | 重构 APIClient | 网络请求失败时的提示逻辑调整，请重点回归弱网和接口异常场景 `[内部改动]` |
| `fix: 修复车门解锁失败无提示` | 修复 DoorService bug | 车门解锁失败时返回失败结果，用户提示由 UI 层展示（本次是否完成需确认） |
| `chore: 补充文案` | 补充 Localizable.strings | 远程控制相关文案补齐，切换语言后可见 |

规则：

1. **写变化，不写实现**：不出现类名、方法名、设计模式，除非测试需要知道
2. **写影响，不写过程**：不写「改了 3 个文件」，写「哪些功能会受影响」
3. **不确定就标注**：无法判断用户可感知变化的，写 `[内部改动，建议回归 XX 场景]`
4. **不编造需求号**：commit 里没有的单号不要填，写 `[待填]`
5. **一条改动对应一个来源**：附上短 commit hash，方便追溯

### 第 5 步：推导影响面

两层：

**直接层**：改动的文件属于哪个模块。有 `.regression-map.yml` 就读它，没有就按目录和文件名推断。

**间接层**：下面这些是车联网 / 移动端的高危公共面，只要改动沾边就要列出来：

- 登录态、token 刷新、账号切换
- 网络层、超时、重试、错误提示
- 车辆控制指令（空调、车门、寻车、充电）
- 权限（定位、蓝牙、通知、相机）
- 多语言、深色模式、大字体
- 启动流程、首页数据加载
- 埋点、推送、分享

无法确定是否受影响时，写进「风险与注意事项」让测试判断，不要假装确定。

### 第 6 步：按模板成文

保存到 `提测单/<版本号>-<YYYYMMDD>.md`。用户指定路径优先；同名文件先问是否覆盖。

```markdown
# <项目名> <版本号> 提测说明

## 一、基本信息

| 项目 | 内容 |
|------|------|
| 版本号 | <版本号> |
| 分支 | `<target>` |
| 提交范围 | `<base>..<target>`（<N> 次提交） |
| 提测人 | <姓名> |
| 提测日期 | <YYYY-MM-DD> |
| 目标环境 | <测试环境 / 预发环境> |
| 关联需求 | <需求号 / [待填]> |

## 二、改动概览

- 共 <N> 项改动：新功能 <a> 项、缺陷修复 <b> 项、优化 <c> 项、配置/资源 <d> 项
- 涉及模块：<模块 1>、<模块 2>、<模块 3>
- 整体风险：<低 / 中 / 高>（判断依据：是否涉及主流程、车辆控制、支付、登录态）

## 三、改动清单

| # | 模块 | 类型 | 改动说明（用户可感知） | 影响范围 | 测试重点 | 来源 |
|---|------|------|------------------------|----------|----------|------|
| 1 | 远程空调 | 新功能 | 车辆列表新增「远程开空调」入口，可设置温度启动 | 车辆列表、远程控制 | 启动成功/失败、温度边界、重复点击 | `499b66a` |

## 四、重点测试场景（P0）

1. <一句话场景>
2. <一句话场景>

## 五、一般测试场景（P1 / P2）

- <场景>
- <场景>

## 六、风险与注意事项

- <风险点：为什么会出问题、测试需要留意什么>
- <依赖项：服务端接口、第三方 SDK、环境配置是否就绪>

## 七、已知问题 / 遗留

- <已知未修复的问题；没有就写「无」>

## 八、回滚方案

- 回滚版本：<上一个稳定 tag / commit>
- 回滚方式：<重新打包 / 关开关 / 服务端降级>
- 数据兼容：<是否有不可逆的数据变更>
- 注意事项：<回滚后需要清缓存 / 重新登录 / 通知测试>

## 九、环境与账号

- 环境地址：<测试环境地址>
- 测试账号：<账号说明>
- 特殊配置：<需要打开的开关、需要绑定的车辆>
```

章节顺序不要改。没有内容的章节写「无」，不要删。

### 第 7 步：自检

1. **每条改动有来源**：要么对应 commit hash，要么对应文件；找不到来源的删掉
2. **每条改动是「人话」**：把「重构 / 封装 / 抽象」这类词删掉，换成测试能验证的描述
3. **测试重点可执行**：写「温度设为 -1 时应有校验」，不要写「测试温度边界」
4. **没有编造**：需求号、已知问题、回滚版本，不确定就写 `[待确认]`
5. **风险等级有依据**：高风险必须说明为什么
6. **和改动数量对得上**：概览的统计和清单行数一致

最后向用户汇报：文件路径、改动项数、涉及模块、整体风险等级，并提醒「关联需求」和「已知问题」两处需要人工补充。

## 无本地环境时（飞书 Aily / 纯对话）

让用户粘贴以下任意一种内容：

- `git log --oneline main..HEAD` 的输出
- 这次改动的文件列表
- 一段改动说明

然后按第 3~6 步同样处理，提测单直接输出在对话里。缺少 commit 来源时，用文件名代替。

## 验证方式

```bash
# 1. 生成演示仓库（含 4 次提交和 v1.1.0 标签）
bash <skill目录>/examples/make_demo_repo.sh

# 2. 收集变更
bash <skill目录>/scripts/collect_changes.sh \
  --repo <演示仓库> --base main --target feature/remote-control \
  --out /tmp/demo-changes.txt

# 3. 按本 skill 流程生成提测单
```

演示仓库的 4 次提交覆盖了新功能、缺陷修复、重构、文案四类，正常情况下应生成一份包含 4 条改动的提测单，且「远程空调」和「车门控制」都要出现在影响模块里。

## 常见错误

| 错误 | 正确做法 |
|------|----------|
| 把 commit 标题原样堆进表格 | 翻译成用户可感知的变化，写不清就标 `[内部改动]` |
| 影响范围只写改动的文件 | 还要考虑公共模块、登录态、网络层、多语言等间接影响 |
| 测试重点写成「测试一下」 | 写成可执行的验证步骤和预期结果 |
| 编一个需求号或版本号 | 不确定就写 `[待填]`，让用户补 |
| 风险等级一律写「低」 | 涉及车辆控制、支付、登录态就至少「中」，并说明理由 |
| 漏掉回滚方案 | 每次提测都要有，哪怕只写「回滚到上一个 tag」 |
| 把内部重构写成新功能 | 用户不可感知的改动标内部改动，避免测试做无效回归 |
